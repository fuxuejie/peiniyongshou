## 一、项目 30 秒电梯演讲

**"陪你永瘦"** 是一款基于**微信小程序 + 腾讯云开发**的健康减脂管理工具，核心亮点是集成了 **AI 多模态识别能力**——用户只需拍照或输入文字（如"跑步30分钟"），AI 就能自动估算热量和营养素。整个项目我通过 **VibeCoding（AI 辅助编程）**方式独立完成，从需求构思到上线部署全链路使用 CodeBuddy AI IDE 辅助开发。

**关键数据**：
- 6 个功能页面、1 个核心 AI 云函数、75 条开发规则驱动
- 技术栈：微信小程序原生 + TDesign UI + CloudBase NoSQL + 混元大模型
- 核心创新：动态图片压缩算法 + 四级 JSON 容错机制 + AI 多模态识别

## 三、关键技术决策及权衡考量

### 决策 1：为什么用纯 CSS 实现柱状图而非引入 ECharts？

**选项对比**：
| 方案 | 优点 | 缺点 |
|------|------|------|
| uCharts/ECharts | 功能强大、交互丰富 | 包体积 200KB+，超出小程序主包限制 |
| Canvas 手绘 | 灵活可控 | 开发成本高，需要处理 DPR 适配 |
| 纯 CSS div | 包体积几乎为零 | 只能做简单柱状图/条形图 |

**最终选择**：纯 CSS div 实现柱状图

**理由**：
1. 项目只需要简单的垂直柱状图，不需要复杂的交互
2. 通过 `height:百分比` 动态控制柱高，`wx:for` 循环渲染
3. 节省的包体积可以留给 TDesign 组件库
4. **PM 思考**：功能够用就好，不过度工程化

```wxml
<!-- data.wxml 中的柱状图实现 -->
<view class="bar-fill {{item.calorie > targetCalorie ? 'bg-orange' : 'bg-green'}}"
      style="height: {{(item.calorie / 2500) * 100 > 100 ? 100 : (item.calorie / 2500) * 100}}%">
</view>
```

### 决策 2：为什么选择 CloudBase NoSQL 而非 MySQL？

**选项对比**：

| 维度 | NoSQL（文档数据库） | MySQL（关系型数据库） |
|------|---------------------|---------------------|
| 学习曲线 | 低，JSON 即存即用 | 高，需要设计表结构 |
| schema 灵活性 | 高，字段可随时增减 | 低，需要 ALTER TABLE |
| 查询能力 | 基础查询足够 | 复杂 JOIN、聚合 |
| 适合场景 | 记录型数据、快速原型 | 复杂业务关系、事务要求 |

**最终选择**：NoSQL 文档数据库

**理由**：
1. 减脂记录是典型的"写入多、关系简单"场景
2. VibeCoding 阶段需求变化频繁，NoSQL 的灵活 schema 更适合快速迭代
3. SDK 调用极其简洁：`db.collection('DietRecord').add({ data: {...} })`
4. **PM 思考**：MVP 阶段优先选择开发效率最高的方案，后续可迁移

### 决策 3：AI Prompt 工程的设计哲学

**饮食识别 Prompt 的三层防御设计**：

```javascript
// 第一层：角色设定 + 专业背景
systemPrompt = `你是一位拥有20年经验的顶尖临床营养师...`;

// 第二层：输出格式强制约束（最高指令）
`绝不允许输出任何废话！严禁输出 Markdown 代码块！必须是从 "[" 开始到 "]" 结束的合法 JSON 数组！`;

// 第三层：反抄袭机制
`警告：以上 JSON 仅为格式演示！严禁照抄里面的数值...`;
```

**踩过的坑**：
- ❌ 最初只说"请返回 JSON"，大模型经常附带 ```json 标记或解释文字
- ❌ 给了示例数值后，模型有时直接照抄示例而不看图片
- ✅ 最终方案：**最高指令 + 反复强调 + 后端四级容错兜底**

**PM 洞察**：和大模型协作就像和不完美的实习生合作——你需要把需求说得极其明确，并且永远做好他理解错的准备。

## 四、踩坑经历与解决方案（面试高分段落）

### 🔥 坑 1：微信云函数 256KB 传输硬限制

**问题描述**：
用户拍摄的高清照片（通常 3-8MB）通过 `wx.cloud.callFunction` 传给云函数时，base64 编码后的字符串轻易超过 256KB，导致请求直接失败。

**错误信息**：
```
Error: invoke cloud function failed: request entity too large (max: 256KB)
```

**解决方案：四档梯级动态压缩算法**

```javascript
// ai-modal 组件中的压缩逻辑（伪代码）
const COMPRESSION_LEVELS = [
  { maxWidth: 600, quality: 0.5 },   // 第1档：轻度压缩
  { maxWidth: 400, quality: 0.3 },   // 第2档：中度压缩
  { maxWidth: 300, quality: 0.2 },   // 第3档：重度压缩
  { maxWidth: 250, quality: 0.1 }    // 第4档：极限压缩
];

async function compressAndUpload(imagePath) {
  for (let level of COMPRESSION_LEVELS) {
    const compressed = await compressImage(imagePath, level);
    const base64 = wx.getFileSystemManager().readFileSync(compressed.tempFilePath, 'base64');
    
    if (base64.length < 100000) {  // 安全阈值 ~100KB 字符
      return base64;  // 压缩成功，返回
    }
  }
  throw new Error('图片过大，无法压缩至安全范围');
}
```

**效果**：99% 的食物照片可以在第 1-2 档成功压缩并保持识别精度

**经验总结**：
- 平台限制是硬约束，必须在设计阶段就考虑
- 渐进式降级比一次性失败更友好
- **测试！测试！测试！** 这个问题在真机测试时才发现，模拟器上不会触发

### 🔥 坑 2：大模型 JSON 输出的不可靠性

**问题描述**：
即使 Prompt 写得再严格，大模型返回的 JSON 仍然会出现各种异常格式：
- 附带 ```json ... ``` markdown 标记
- 返回对象而非数组
- 中文 key 名（"热量": 350）
- 尾部缺少 `]` 或 `}`
- 在 JSON 前后添加解释文字

**解决方案：四级容错架构**

```
Level 1: Markdown 剥离
  "```json\n[{...}]\n```" → "[{...}]"

Level 2: 正则提取 JSON 块
  从混杂文本中用 /\[[\s\S]*\]/ 提取 JSON 数组

Level 3: 结构修复
  缺少尾部 ] 或 } 时自动补全

Level 4: 暴力正则兜底
  当 JSON.parse 彻底失败时，
  直接用正则从原始文本中提取 name/calorie/carbs 等字段
```

**代码精华**（ai-record 云函数）：

```javascript
// Level 1-3: 结构化容错
let jsonStr = result.text.trim();
// 剥离 markdown 标记
if (jsonStr.startsWith('```json')) jsonStr = jsonStr.substring(7);
// 正则提取 JSON 块
const arrayMatch = jsonStr.match(/\[[\s\S]*\]/);
// 补全缺失的括号
if (!extractedJsonStr.endsWith(']')) extractedJsonStr += ']';

try {
  aiData = JSON.parse(extractedJsonStr);
} catch(e) {
  // Level 4: 暴力正则兜底
  aiData = [{
    name: rawText.match(/"name"\s*:\s*"([^"]+)"/)?.[1] || '未知食物',
    calorie: rawText.match(/"calorie"\s*:\s*(\d+)/)?.[1] || 0,
    carbs: rawText.match(/"carbs"\s*:\s*(\d+)/)?.[1] || 0,
    protein: rawText.match(/"protein"\s*:\s*(\d+)/)?.[1] || 0,
    fat: rawText.match(/"fat"\s*:\s*(\d+)/)?.[1] || 0
  }];
}
```

**额外智能聚合**：
当大模型返回多个食材时，自动汇总为"一整份"选项放在数组首位：

```javascript
// 多食材自动聚合为"整份"汇总项
if (formattedData.length > 1) {
  const totalCal = formattedData.reduce((sum, item) => sum + item.calorie, 0);
  formattedData.unshift({
    name: `🍱 一整份 (${foodNames})`,
    calorie: totalCal,
    // ...
  });
}
```

**经验总结**：
- **永远不要信任 LLM 的输出格式**——它是概率模型不是编译器
- 容错设计应该像洋葱一样一层层剥开，每层都有 fallback
- 产品体验 > 数据完美：宁可给出一个大概的热量估计，也不要报错让用户困惑

### 🔥 坑 3：本地存储的跨天边界问题

**问题描述**：
用户的喝水打卡数 stored in local storage，但如果用户在 23:59 打卡一次，第二天打开 app 时数据没有重置，导致"昨天喝的水算到了今天"。

**解决方案**：日期比对 + 自动重置

```javascript
// index.js 中的跨天检测
const today = `${today.getFullYear()}-${today.getMonth() + 1}-${today.getDate()}`;
const waterDate = wx.getStorageSync('waterDate');

if (waterDate !== todayStr) {
  waterCount = 0;  // 新的一天，重置计数
  wx.setStorageSync('waterCount', 0);
  wx.setStorageSync('waterDate', todayStr);
}
```

**经验总结**：
- 本地存储的状态管理需要显式处理生命周期
- 所有"每日重置"的数据都要绑定日期校验
- 这类 bug 在正常工作时间测试很难发现，需要在午夜前后专项测试

---

### 🔥 坑 4：TDesign 组件在小程序中的样式冲突

**问题描述**：
TDesign 组件的全局样式会污染自定义组件的样式空间，导致某些圆角、颜色被覆盖。

**解决方案**：
- 使用 CSS 变量体系统一管理色彩（`--primary: #10B981`）
- 自定义组件增加 `styleIsolation: 'apply-shared'`
- 关键样式使用 `!important` 或更高优先级选择器

**经验总结**：
- 第三方组件库的样式隔离问题是小程序开发的常见坑
- 建立统一的 Design Token（设计变量）体系可以减少很多样式冲突

> "最大的挑战是**大模型的输出不可控性**。
>
> 具体来说，当我接入腾讯混元视觉模型来做食物热量识别时，即使我在 Prompt 里反复强调'只输出 JSON'，它还是经常会返回带 markdown 标记的文本、或者夹杂解释文字、甚至用中文 key 名。
>
> 一开始我用了很 naive 的方式——直接 `JSON.parse()`，结果线上经常报错。后来我重新设计了**四级容错架构**：
> - 第一级剥离 markdown 标记
> - 第二级用正则提取 JSON 块
> - 第三级补全缺失的括号
> - 第四级当 JSON.parse 彻底失败时，用暴力正则逐个提取字段
>
> 还有一个**智能聚合逻辑**：当 AI 识别出一张图里有多个食材时，我会自动汇总成一个'一整份'选项放在首位，因为大多数情况下用户只想记'这顿饭总共多少热量'。
>
> 这个经历给我的启示是：**和 AI 协作就像和不完美的员工合作——你要把需求说得极其明确，并且永远做好他理解错的准备。这也让我对 AI 产品的边界有了更深的理解。**"

> - **第一，Prompt Engineering 本质上是需求分析能力的延伸**——你越能把需求说清楚，AI 的产出越好
> - **第二，技术鉴赏力变得更重要**——你不需要会写代码，但要能判断 AI 写的对不对、有没有安全隐患
> - **第三，产品判断力的价值被放大**——AI 可以帮你实现 10 个功能，但你得知道哪个值得做

## 七、可能追问的应答准备

### Q: "你不懂后端，怎么保证代码安全性？"

**A**:
1. **CloudBase 平台自带安全能力**：数据库权限可在控制台精细化配置（仅创建者可读写、管理员可读写等）
2. **云函数天然隔离运行**：每个函数在沙箱环境中执行，不存在注入风险
3. **AI 规则体系约束**：CodeBuddy 的 75 条规则文件包含安全最佳实践（如 SQL 注入防护、XSS 防护等）
4. **人工 Review 环节**：每一轮 AI 生成的代码我都会审查后再合并

### Q: "这个项目的用户量如何？有什么数据？"

**A**（根据实际情况调整）:
- 目前主要作为**个人项目/作品集**在使用
- 核心验证的是 **VibeCoding 开发模式的可行性**，而非商业化指标
- 如果面试官关注规模化，可以讨论的方向：
  - 引入用户系统（CloudBase Auth）
  - 社交分享裂变（已有分享功能基础）
  - 付费增值服务（定制化饮食方案等）

### Q: "如果让你重新做一遍，你会改变什么？"

**A**:
1. **更早做技术验证**：256KB 图片限制应该在 Day 1 就做 PoC，而不是 Day 5 才发现
2. **引入单元测试**：特别是 AI 容错逻辑，应该有自动化测试覆盖各种异常输入
3. **组件化做得更彻底**：一些重复的 Modal 弹窗逻辑可以抽成通用组件
4. **加入埋点和 analytics**：从一开始就关注数据，而不是后期补
